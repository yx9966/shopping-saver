# 算价输入

这是候选订单比较器。Agent 收集实时页面与规则后录入 JSON；脚本不负责抓取平台、不验证网页真伪，也不自动发现遗漏的组合。先确认同款和优惠资格，再录入金额。

所有金额单位是人民币分，必须为非负整数。每个 `item` 对应一个确定型号、规格的商品，`needs` 给出购买数量。同款在不同平台沿用相同 ID；包装不同需先按用户需求换算并核验，不能只改 ID 当成同款。

## 顶层

| 字段 | 含义 |
|---|---|
| `needs` | 商品 ID 到正整数数量的映射，1–5 种、合计最多 20 件 |
| `max_filler_cents` | 整套方案额外商品优惠前总额上限；未授权凑单时填 0 |
| `orders` | 最多 40 个候选结算组合，每个最多使用一次 |

## 候选订单

每单必填 `id`、`platform`、`lines`、`discounts`、`shipping_cents`、`resources`、`evidence`、`valid_until`。允许可选 `valid_from`、`checkout_total_cents`、`other_fees_cents`。未知字段报错，避免误拼字段导致漏算。

- `id` 唯一；`platform` 写平台及店铺，或说明是同平台跨店结算。
- `lines` 每行包括 `item`、`quantity`、`unit_cents`、`url`。同一单不重复商品 ID，数量合并。`needs` 之外的商品全部按凑单计算，且必须是用户接受的商品。
- `unit_cents` 是所列优惠应用之前的实际单价。商品价已包含的折扣不能再次写进 `discounts`。明确限购、库存及每件是否同价。
- `discounts` 按真实应用顺序排列；不用券的候选订单填空数组。
- `shipping_cents` 是该候选组合已确认的最终运费（所有店铺之和）。脚本不推断免邮门槛。运费未知的订单暂不进入主推荐。
- `other_fees_cents` 是该组合已确认必须另付的税费、服务费等，非负整数分，默认 0；只有确认没有此类费用时才省略，不能把未知税费当零。已包含在商品价或运费中的费用不重复计入。它参与最低总支出排名，不参与优惠门槛或商品券抵扣；明细与来源保留在证据中。脚本不自动分摊跨订单共享费用；有共享费用时先形成完整结算候选，不能重复加收或漏收。
- `resources` 是只能用一次的权益 ID，例如 `jd:account:coupon-123`。同一张券在不同候选中必须使用同一 ID。可以写多个 ID，表达券、补贴、限购等约束；跨订单互斥权益也共享同一 ID。可重复的普惠活动不占一次性 ID。同单互斥券应拆成不同候选，不得同时录入。
- `evidence` 只有 `source`（官方 URL 或用户截图文件路径）和 `observed_at`（带时区 ISO 时间）。这是该完整组合的证据；详细优惠来源与适用规则另在会话或任务笔记中保留。
- `valid_until` 取所有商品报价与优惠共同可用的最早截止时间，不包含该时刻。`valid_from` 包含该时刻，默认查询时间。未公布截止时间时用保守的复查期限，并向用户说明这是复查期限，不是官方活动截止。报价在未开始或已过期的候选会被排除。
- `checkout_total_cents` 只录入完整结算页实际显示的付款总额，与计算结果不符会报错。不可为了得到已核验标记而复制脚本金额。

涉及新开会员、定金、支付返现或未确认补贴的报价，第一版不自动建模。默认用已有资格下的即时付款金额进行比较，并另列未纳入机会。

## 优惠规则

每条必须包含这六个字段，`id` 在同单内唯一：

```json
{
  "id": "店铺满300减50",
  "items": ["a", "b", "tissue"],
  "basis": "original",
  "threshold_cents": 30000,
  "off_cents": 5000,
  "repeat": false
}
```

`items` 是该单参与此优惠的商品 ID，不能省略或把未参与的商品凑进去。`basis: original` 按这些行的优惠前金额判断门槛；`remaining` 按之前优惠扣除后的金额判断。`repeat: true` 是每满减，门槛必须大于零；`false` 只减一次，门槛为零可表示无门槛立减。抵扣不超过参与商品剩余金额，运费不参与商品券。

优惠按参与商品的剩余金额同比例分摊，余分按最大余数分配，再按商品 ID 排序打破平局。这个规则是明确的估算模型，不保证与平台分摊规则一致。后续门槛依赖分摊、金额恰好卡线或存在分摊差异时，必须用结算页核验，不将估算当作可下单价格。

从结算页录入脚本不支持的复杂优惠时，可用门槛为零的明确差额记录，但只能用于该确切商品组合，不可推演到其他商品、数量或时间。

## 运行与结果

```sh
python3 <skill-directory>/scripts/compare.py input.json --output result.json
```

默认按运行时刻排除失效订单。`--at 2026-10-13T12:00:00+08:00` 只用于历史回放与合成测试，不用于伪造当前优惠有效。

退出码：0 有完整方案；1 无完整可行方案；2 输入有误或搜索超限。无完整方案时，`uncovered_items` 仅表示完全没有候选覆盖的商品；若它为空，仍可能因为数量、互斥券或凑单预算而无解。不能输出不完整购物清单的总价。

`plans` 包含 `lowest_total`（总支出优先）、`lowest_verified`（每单均有一致的结算页金额，按总支出优先）、`fewest_orders`（结算组合数量优先）、`without_filler`（无凑单最低支出）。相同方案展示一次即可。每个方案保留订单、优惠、运费、其他必要费用、证据和核验状态；总额包含全部凑单商品。`saving_vs_without_filler_cents` 只和已提供的无凑单候选比较，没有基线时返回 null。

`lowest_total` 可能比 `lowest_verified` 更便宜，但前者含估算时需明确标记。`lowest_verified=null` 表示没有完整已核验方案，不代表没有优惠。此核验状态依赖 agent 诚实录入当前账号结算页，脚本不会自行验证截图、账号或资格。所有方案都必须先经 agent 筛掉不满足用户店铺、同款、数量、地区和优惠资格的候选；脚本不判断这些语义条件。

这里的订单数是候选结算组合数，跨店结算后可能生成多个物流订单，面向用户应按实际情况解释。
